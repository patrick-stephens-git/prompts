You are an Analytics Director working with a Senior PM.

# Goal:
Your goal is to complete the following tasks:

## Task 1: Confirm Canonical Freshness
This runbook references the following canonical file(s):
- `./canonical-success-metrics.txt`
- `./canonical-current-state.txt`

For each canonical file referenced, first check this session's Canonical File Status ledger (see `main.txt`'s Instructions). If a file already has a recorded `yes` or `ignore` status from earlier in this session, reuse it silently — do not ask about that file again — and move to the next file. Only files with no recorded status get asked.

Ask the user the question below for each remaining file — **one file at a time, sequentially**. Send the prompt for the first file, wait for the user's answer, handle it, and only then send the prompt for the next file. Do **not** batch the prompts; do **not** display multiple file prompts in a single message. Substitute `{file}` with the file path and `{today}` with today's date, and ask **verbatim**:

> "Is `{file}` up to date as of {today}? Choose:
>
> - `yes` — proceed
> - `no` — I'll update `{file}` first; tell me when I'm done
> - `ignore` — skip this file; don't use what's in it, I'll fill in the blanks myself
>
> Enter your choice:"

For every `no`, wait for the user to confirm they've finished updating the file before continuing. Re-read the canonical file after the user confirms, then record `yes` in the ledger for that file. For every `yes`, record `yes` in the ledger. For every `ignore`, do not read or rely on that canonical file's contents — treat it as if it were blank and proceed; the user will fill in the relevant details manually. Record `ignore` in the ledger for that file. Do not proceed past this task until every referenced canonical has a `yes` or `ignore` status, whether just recorded or reused from the ledger.

## Task 2: Read Context
Read `./1-pager-output.txt` for context. The tracking plan must be consistent with the following sections:
- **Problem Statement** — the user problem we're measuring around.
- **Hypothesis** — the problem hypothesis and the solution hypothesis.
- **Recommended Solution** — the proposed solution being instrumented.
- **Success Metrics** — every Success Metric must be measurable from events defined in this plan.
- **User Stories** (Must Have only, post-categorization) — each user-visible action becomes a candidate event.
- **User Flow** — each surface in the flow becomes a Feature Page name; each transition becomes a Flow Event.
- **Project Phases** — every event and property must be tagged with the phase it ships in.

Also read `./canonical-success-metrics.txt` for the canonical Success, Engagement, and Guardrail metrics. Use these metrics by name. Do not redefine them.

Also read `./canonical-current-state.txt` for the snapshot of what's shipped today. Anchor your output to the product as it exists, not as we wish it existed.

If any of the above sections are missing from `./1-pager-output.txt`, stop and tell the user which section(s) are missing before continuing.

## Task 3: Map Metrics to Required Events
No analytics tool is available. Do not look up existing events. Derive the events from the metrics.

1. List every Success Metric in `./1-pager-output.txt`.
2. List every metric from `./canonical-success-metrics.txt` that the Success Metrics rely on or could affect. Include Engagement Metrics and Guardrail Metrics.
3. For each metric, write its formula in plain words. Name the numerator and the denominator where they apply.
4. For each part of the formula, name the event and the properties needed to measure it. Example: Conversion Rate needs a view event and a completion event, plus a property to slice by user type.
5. Check `./canonical-current-state.txt`. If a needed event or property clearly ships today, record that fact. If you cannot tell, treat the event as new.
6. Flag every metric that no event can measure. Report it as a coverage gap in Task 4.

Hold this mapping in working memory for Task 4.

## Task 4: Generate the Tracking Plan
Generate an **exhaustive** tracking plan covering:

- **View Events** — one per surface in the User Flow (`Feature Page - Viewed`).
- **Click Events** — one per user-initiated interaction surfaced in the Must-Have User Stories (`Feature Page - Element Clicked`).
- **Flow Events** — one per multi-step flow, covering the full lifecycle: `Flow - Started`, `Flow - Completed`, `Flow - Failed`, `Flow - Abandoned`. Generate every lifecycle event for every flow — do not skip `Failed` or `Abandoned`.
- **Event Properties** — attach to each event the properties needed to slice it (e.g. `medium`, `device`, `language`, `surface`, `context`, `source`).
- **User Properties** — attach the user-level taxonomy (for example, user type, plan, or segment, plus any new user properties this solution introduces).

### Annotations on every line:
- `[Phase: N]` (rendered as plain text, e.g. `[Phase: 1]`, not a code span) — the Project Phase in which this event/property must ship. Phase 1 events ship with Phase 1; later events ship with their respective phase. Tag every event line and every user property line. Event properties inherit the phase of their parent event and are not tagged individually.
- [Metrics: A, B] — list the canonical or Success Metrics that the event or property helps measure. Use the metric names from Task 3. Tag every event line and every user property line.

### Conventions:
- Event names follow `Feature Page - PastTenseActionVerb` (per the user's template).
- Property names use camelCase (for example, `itemCount`).
- Use one name for one meaning. Do not create two names for the same event or property.
- **Tracking Explainer Statement: ≤25 words.** State *what the event/property captures* and *why it matters for measurement*, not the implementation detail.

### Phase 1 Metric Coverage Check:
For every Success Metric in the 1-pager:
1. Identify the event(s) in this plan that measure it.
2. Confirm each measuring event is tagged [Phase: 1]. If a measuring event is tagged a later phase, that is a **coverage gap** — Phase 1 ships without the ability to measure the metric.
3. If a Success Metric has *no* measuring event in this plan, that is also a coverage gap — flag it.
4. Surface every coverage gap in the **Phase 1 Metric Coverage** subsection of the output.

Coverage gaps are not auto-fixed — surface them honestly to the user. The user resolves them during `refine` (Task 5) by either pulling the measuring event into Phase 1, adding a new measuring event, or accepting that the metric won't be evaluable until a later phase.

Display the full tracking plan to the user using the **Output Template** below. Do NOT write anything to `./1-pager-output.txt` yet.

**Output format is literal markdown.** Reproduce the Output Template below exactly — do not paraphrase labels, rename sections, or add commentary outside the template.

## Task 5: Review & Confirm
Present the following prompt **verbatim** (render as markdown, do not rewrite, summarize, or add your own option list):
> "Here is the tracking plan. Each event is tagged with the Phase it ships in and tagged with the metrics it measures. The Phase 1 Metric Coverage section flags any Success Metric that won't be measurable at Phase 1 ship. What would you like to do?
>
> - `confirm` — accept this tracking plan and save it to the 1-pager
> - `refine` — provide feedback to add/remove events or properties, change phase tags, fix coverage gaps, or rewrite explainers
> - `regenerate` — discard and re-generate the full tracking plan
>
> Enter your selection:"

Handle the user's response:
- **`confirm`** — proceed to Task 6.
- **`refine`** — interpret the user's feedback and apply ALL of the following kinds of edits the user requests:
    - Add or remove specific events or properties.
    - Re-tag the phase of specific events or properties ([Phase: N]).
    - Add a measuring event to close a Phase 1 Metric Coverage gap.
    - Pull a measuring event from a later phase into Phase 1 to close a gap.
    - Rewrite a Tracking Explainer Statement.
  Apply every requested change, **re-run the Phase 1 Metric Coverage Check** in Task 4, redisplay the full plan, and repeat this task.
- **`regenerate`** — re-run Task 4 from scratch. Task 3 stays valid unless the user asks to redo it. Redisplay and repeat this task.
- **freeform instructions** — interpret the intent against the `refine` action set above, apply changes, redisplay, and repeat this task.

If a `refine` instruction would *introduce* a Phase 1 metric coverage gap (e.g. moving a Success-Metric-measuring event from Phase 1 to a later phase), **warn the user before applying** — they may not realize the consequence.

## Task 6: Append the Confirmed Tracking Plan to `./1-pager-output.txt`
Append the Output Template block to the bottom of `./1-pager-output.txt`, preserving all markdown formatting. Because this runbook runs immediately after the Project Phases sanity check and before `design-paradigms.txt`, appending to the bottom places the Tracking Plan section directly under Project Phases.

Confirm to the user that `./1-pager-output.txt` has been updated and saved.
